# NetFreedom

Открытый, локальный и обратимый инструмент доступа к открытому Интернету из России.
Два режима работы в одном исполняемом файле:

| Режим | Команда | Что делает |
|---|---|---|
| **Игры через WARP** (по умолчанию) | `netfreedom start` | встроенный движок защищает только рукопожатие Cloudflare WARP (QUIC/UDP), весь игровой трафик идёт внутри туннеля |
| **Обход без WARP** | `netfreedom start --bypass` | стратегия сама разблокирует сайты за Cloudflare, YouTube, Discord (и, по желанию, порты игр) |

Windows: встроенный движок на Rust + драйвер WinDivert (отдельного `winws.exe` и Cygwin больше нет). Linux: `nfqws` + nftables. Философия проекта: [PHILOSOPHY.md](PHILOSOPHY.md)
(или `netfreedom about`). Репозиторий: https://github.com/PsyGioX/NetFreedom

## Быстрый старт

```text
netfreedom                       интерактивное меню
netfreedom tune                  подобрать лучшую стратегию для игр на вашем провайдере
netfreedom tune --bypass         то же для обхода без WARP (по реальным загрузкам)
netfreedom start                 запуск; затем главное меню со статусом, остановка — пункт 1 или закрытие окна
netfreedom doctor                диагностика системы
netfreedom doctor --net          + Wi-Fi или кабель, фоновый трафик, задержка под нагрузкой
netfreedom check <IP> --load     пинг/джиттер/потери + задержка под нагрузкой (bufferbloat)
netfreedom verify                проверка целостности пакета (SHA-256)
```

Нужны права администратора (Windows) или root (Linux). Окно не закрывается само: результаты
всегда остаются на экране до нажатия Enter.

## 3.3: быстрая проверка, живой мониторинг с данными, Vercel/Netlify, пересмотр стратегий

* **Тест качества больше не «висит».** Трассировка Cloudflare, ICMP и TCP идут параллельно (раньше
  складывались: до ~50 с на плохой линии). У каждой фазы потолок по времени (15 с), а если узел молчит,
  фаза прекращается после 6 безответных проб. Потери считаются от реально отправленных проб, поэтому
  досрочная остановка не рисует «100 % потерь» на живой линии. Загрузка 300 КБ идёт строго после
  замеров задержки, иначе она сама раздувала бы пинг. В отчёте появилась строка «Заняло: N с».
* **Живой мониторинг в режиме обхода.** Первая проверка сайтов через 8 с (было 60), затем каждые 2 минуты
  (было 5). Панель называет закрытые сайты поимённо и отмечает те, что недоступны на уровне IP/DNS.
  Если стандартный узел 1.1.1.1 молчит (часть провайдеров режет ICMP/TCP к нему), монитор сам переходит на
  8.8.8.8, 9.9.9.9, 77.88.8.8. Узел, который вы задали сами (пункт 5), не подменяется.
* **Понятная причина тайм-аута.** «Connection timed out» на этапе connect означает, что адрес сервера не
  отвечает на первый же пакет (блокировка по IP или подмена DNS). Стратегия SNI/TLS этого не лечит.
  `tune --bypass` после трёх замеров перестаёт ждать такие сайты (экономит ~5 с на сценарий) и в конце
  пишет, что им нужны DoH/другой резолвер, WARP или прокси.
* **Vercel и Netlify.** Новый `lists/list-dev.txt` (vercel.app, vercel.com, netlify.app …) подключён ко
  всем стратегиям, а проверка получила цели Vercel и Netlify. Данные о блокировке противоречивы:
  часть владельцев сообщает о блокировке IP Vercel для собственных доменов при работающем `*.vercel.app`.
  Если блокировка по IP, SNI-стратегия не поможет.
* **Пересмотр стратегий (29 вместо 28).** Новая `hostfake-g`: `hostfakesplit` с хостом google.com и `ts`
  (так в 2026 году устроено правило YouTube у Flowseal). У собственных стратегий с фейками появилось отдельное
  правило для `googlevideo.com`: у части абонентов МГТС и Ростелекома страница YouTube открывается, а видео
  нет (Flowseal/zapret-discord-youtube#17781). Добавлено QUIC-правило для YouTube (раньше QUIC к YouTube
  не покрывался ни одним правилом). Проверенные оригинальные стратегии оставлены дословно, а бесфейковые
  (`split`, `sni-split`, `general`, `alt2`) остаются без фейков. Быстрый набор `--quick` обновлён:
  `balanced, disorder, max, hostfake-g, hostfake, alt9, alt11, alt12, alt13, split`.

## 3.2: честные проверки, главное меню со статусом, надёжность и безопасность

**Меню вместо «Enter для остановки».** После запуска программа возвращается в главное меню с живой
панелью: активен ли режим, подтверждён ли туннель (`warp=on`, дата-центр, IP), задержка, джиттер и потери
за последнюю минуту, состояние движка и WARP, последние события. Остановить всё можно пунктом «Остановить»
или просто закрыв окно (Ctrl+C, выход из системы и выключение тоже всё возвращают). Пункт «Живой мониторинг»
перерисовывает панель каждую секунду. Клавиши работают и в русской раскладке (`ы` = S, `д` = L).
Язык: русский по умолчанию, `L` переключает на English (запоминается).

**Почему прежний тест после подключения врал.**
1. «Connected» в `warp-cli` означает лишь, что демон закончил рукопожатие. Пакеты через туннель при этом могли
   не идти. Теперь трафик проверяется через `cloudflare.com/cdn-cgi/trace`: нужен ответ `warp=on|plus`
   дважды подряд. Нет — результат помечается «НЕ ПОДТВЕРЖДЕНО», а не «отлично».
2. Пинг 1.1.1.1 работает и без WARP, а внутри туннеля показывает только расстояние до ближайшего узла
   Cloudflare. Поэтому проверка качества сверяет ICMP с TCP-замером: если они расходятся в разы, пинг признаётся
   недостоверным. По умолчанию наблюдается ваш игровой сервер (пункт 5 меню), а не 1.1.1.1.
3. Прогрев был один пакет. Теперь отбрасываются три, иначе первые пакеты холодного туннеля портили каждый
   замер после (пере)запуска.
4. Меньше 5 проб или меньше половины ответов не считается измерением и не участвует в сравнении.

**Почему результаты `tune` ухудшались с каждым запуском.** Первый сценарий всегда платил за холодный старт
WARP, а между сценариями следующее подключение начиналось, пока предыдущее ещё закрывалось. Теперь: прогревочное
подключение до измерений (не засчитывается); ожидание реального `Disconnected`; один метод измерения (ICMP или
TCP) для всех сценариев, а не смесь; сценарий засчитывается, только если подтверждён `warp=on`; финалисты
оцениваются по худшему из двух прогонов, а не по среднему.

**Что взято у игровых бустеров (ExitLag, GearUP и др.).** У них ключевое — собственные серверы и мультипуть, их
здесь быть не может (проект локальный и без серверов). Клиентская часть повторена: постоянное измерение пути,
сторож в фоне (перезапуск движка и переподключение WARP с нарастающей паузой), проверка, что трафик реально в
туннеле, раздельная статистика по узлу (дата-центр в панели).

**Безопасность.**
* Утилиты, которые запускаются с правами администратора (`curl`, `netsh`, `sc`, `nft`, `systemctl`, `powershell`…),
  вызываются по абсолютному пути из системных каталогов, а не через `PATH`/текущую папку.
* Linux: журнал `nfqws` перенесён из `/tmp` (любой локальный пользователь мог подложить символическую ссылку, и root
  перезаписал бы чужой файл) в `/run/netfreedom` (0700, `O_NOFOLLOW`, проверка владельца).
* `curl`: только HTTPS (и для редиректов), TLS 1.2+.
* **Автозапуск в Windows** (`netfreedom autostart on`) запускает программу с правами администратора при каждом входе,
  поэтому важно, кто может подменить `netfreedom.exe` и `bin\WinDivert.dll`. Из `C:\Program Files` автозапуск
  включается как есть. Из профиля пользователя (Загрузки, Рабочий стол, Документы, OneDrive, `C:\Users`) он
  **отказывается включаться**: любая программа пользователя может подменить такую папку целиком. Из любой другой
  папки (например `C:\NetFreedom`) он сначала ограничивает её через `icacls` (владелец: Администраторы, запись только
  у SYSTEM и Администраторов, у пользователей чтение и запуск) и только потом создаёт задачу. Папка не должна
  лежать в каталоге, где обычный пользователь может её переименовать. После этого правка списков и
  `utils\netfreedom.cfg` требует прав администратора. Откат прав: `icacls "<папка>" /reset /T`, затем
  `icacls "<папка>" /setowner "<ваш пользователь>" /T`.
* Процессы по имени завершаются только с проверкой пути образа. Другой экземпляр движка: только тот же самый
  `netfreedom.exe`. Discord: только из папок установки Discord. Cloudflare WARP: только из `Program Files\Cloudflare\Cloudflare WARP`.
  Процесс с таким же именем из другой папки не трогается (для Discord и другого экземпляра движка выводится предупреждение). (Остаток: устаревший
  `winws.exe` старых версий и `nfqws` в Linux по-прежнему завершаются по имени.)
* Сборка релиза (`release.yml`): все действия закреплены по SHA коммита, сборка, подпись и публикация разнесены по
  трём job с минимальными правами токена; ключ подписи есть только в job, где нет сторонних действий.
* Программа сама **ничего не скачивает в списки**: команды `lists update` больше нет, списки поставляются в архиве
  релиза (под контролем `SHA256SUMS.txt`) и меняются только вручную.
* Файл настроек пишется атомарно (временный файл и переименование).

## Что изучено и как это отражено в стратегиях

* **ТСПУ** классифицирует соединение по первым пакетам (SNI в TLS ClientHello, QUIC Initial).
  Если классифицировать не получилось, для адресов Cloudflare включается «запасной» режим:
  пропускается лишь около 16 КБ ответа (с 9 июня 2025 у Ростелекома, МТС, МегаФона, МГТС и др.).
  Поэтому проверка обхода — это скачивание файла **больше 16 КБ с Cloudflare**, а не пинг.
* **Фейки с «прошлым» номером последовательности** (`badseq` по умолчанию) ТСПУ начал наказывать
  разрывом соединения (youtubeUnblock#356). В новых стратегиях таких нет: только `ts`, низкий TTL,
  «будущий» seq или вообще без фейков.
* **Перехват DNS** к 8.8.8.8 / 1.1.1.1 через ТСПУ (wiki.zapret.moe, август 2026): `doctor` и
  `tune --bypass` честно показывают, что именно не открылось, а не скрывают проблему.
* **WARP/MASQUE** идёт по QUIC на UDP 443 (+ 500, 1701, 4443, 4500, 8095, 8443) к диапазонам
  Cloudflare. Стратегии WARP выбирают пакеты по IP-диапазону на уровне WinDivert и **не зависят
  от файлов списков**. В старом наборе при `ipset = none` защита рукопожатия молча отключалась.

> Эти выводы получены из публичных источников и кода. На живом ТСПУ каждого провайдера всё
> ведёт себя по-своему — поэтому в проекте есть `tune`.

## После 3.2: локальные причины лага, единая шкала, честный монитор

Что показали сравнение с практикой оптимизации задержки и разбор кода (версия пакета не менялась).

**Задержка под нагрузкой (bufferbloat).** Простой пинг и тест скорости не видят очередей, которые
заполняются, когда кто-то качает или раздаёт: пакеты игры стоят в них позади чужого трафика.
`netfreedom check <IP> --load` и `netfreedom doctor --net` загружают канал (4 потока `curl` на
скачивание, затем на отдачу, по 8 секунд) и пингуют хост во время нагрузки. В отчёте: покой, задержка
(+ прирост) и потери под нагрузкой, достигнутая скорость нагрузки и вердикт. Пороги прироста
(20 / 60 мс) эвристические, их задал проект, это не стандарт. Если нагрузка не набрала скорость
(меньше около 2 Мбит/с), вывода нет: тест не выдаёт «всё хорошо» за пустую нагрузку. Лечится
обычно на роутере: умное управление очередью (SQM: fq_codel или CAKE) и ограничение скорости на
90-95% от реальной. Нагрузка идёт через `speed.cloudflare.com` (тот же адрес, что в проверке обхода).
`doctor --net` дополнительно показывает тип соединения (Linux: кабель, Wi-Fi или виртуальный
интерфейс по маршруту по умолчанию; Windows: подключён ли Wi-Fi и уровень сигнала) и фоновый
трафик (только Linux). Это измерения и подсказки: настройки системы и роутера программа не меняет.

**Прямой путь против WARP в `tune`.** После ранжирования `tune` один раз отключает WARP, измеряет путь
до `--target` напрямую и сравнивает его с лучшим результатом тем же игровым счётом. Вывод: WARP заметно
лучше, разница небольшая или напрямую лучше. Это сравнение задержки, а не доступности: если без WARP
игра блокируется, выбирать надо по доступности. С целью по умолчанию (1.1.1.1) шаг пропускается,
потому что этот адрес отвечает и с WARP, и без него; отключается флагом `--no-direct`.

**Единая шкала качества.** Раньше один замер получал три оценки: «хорошо» до 10 мс джиттера в `check`,
«терпимо» с 6 мс в оценке после запуска и жёлтый с 8 мс в панели. Теперь везде одно правило
(`stats::level`): джиттер до 10 мс и нет потерь: хорошо; до 15 мс, любые потери или длинный хвост:
терпимо; больше 15 мс или потери выше 2%: плохо. Это меняет поведение: оценка после запуска
стала мягче (было «терпимо» с 6 мс, теперь с 10 мс), панель тоже.

**Монитор.** (1) Узел, не отвечающий на ICMP, больше не показывается как «100% потерь»: после пяти
молчаливых ICMP-проб монитор проверяет TCP 443 и, если тот отвечает, переходит на него (метод
виден в панели рядом с адресом). Если молчат оба, потеря настоящая и показывается как потеря.
(2) Замеры (раз в секунду) и тяжёлые проверки (`warp-cli`, трасса Cloudflare через `curl` до 6 с,
загрузка сайтов в режиме обхода) теперь в разных потоках: медленная проверка больше не оставляет дыр в окне
«последняя минута».

## Обход без WARP: 29 стратегий, Instagram, X, Telegram, WhatsApp (3.1, обновлено в 3.3)

`netfreedom start --bypass` и `netfreedom tune --bypass` (быстрый подбор: `--quick`, 10 вероятных стратегий).

* **Стратегии.** Десять собственных (добавлена `hostfake-g`), три варианта вокруг семейства, которое сработало в реальном отчёте
  (`disorder`, `max`: fake + разрезание с таймстампами), и 16 проверенных стратегий исходного набора дословно
  (`general`, `alt`…`alt13`, `exp`, `simple-fake*`, `fta-alt`; нумерация Flowseal). Все 33 стратегии
  (с WARP-вариантами) принимает настоящий `nfqws --dry-run`: `python3 tools/validate_strategies.py`.
* **Instagram и X.** Домены Meta (instagram.com, cdninstagram.com, fbcdn.net, facebook.com …) и X
  (x.com, twitter.com, twimg.com, t.co …) лежат в `lists/list-social.txt`. Файл создаётся автоматически, если его нет, и подключён к QUIC-, TLS- и HTTP-правилам
  каждой стратегии. Свои домены добавляйте в `list-general-user.txt`. Блокировки **по IP-адресу**
  обходом SNI не лечатся: диапазоны Meta и X в `ipset-all.txt` не входят, и честный ответ даст проверка.
* **Telegram и WhatsApp.** Домены (telegram.org, t.me, telegra.ph, whatsapp.com, whatsapp.net, wa.me …) лежат
  в том же `list-social.txt`. Клиенты Telegram подключаются напрямую к адресам, без имени сайта, поэтому
  дополнительно есть `lists/ipset-social.txt` с диапазонами дата-центров Telegram (правило только для порта 443).
  Диапазоны сверены с официальным `cidr.txt` Telegram (в 3.3 добавлены `91.105.192.0/23` и
  `2001:b28:f23c::/48`); проверить самому: `python3 tools/check_social_ranges.py`.
  Честные ограничения (ноябрь 2026): родной протокол MTProto (обфусцированный, не TLS) приёмами TLS не
  лечится, а ТСПУ замедляет Telegram по адресам и по статистике трафика. Рабочий путь для Telegram сейчас:
  локальный `tg-ws-proxy` (WSS к `kws*.web.telegram.org`), см. раздел 3.3. WhatsApp ограничен **по IP-адресам Meta**:
  zapret здесь спасает максимум от ретрансмиссий, но не от замедления по адресу, поэтому домены в списке
  нужны, а чудес ждать не стоит.
  Уже установленная копия не получит новые записи в существующих `list-social.txt` и `ipset-social.txt`:
  удалите файл, и он создастся заново (`list-dev.txt` создаётся сам).
* **Проверка** (`web.rs`) скачивает реальные файлы: Cloudflare 300 КБ (ловит порог ~16 КБ), Discord,
  YouTube, Instagram, X, Telegram (web), WhatsApp (web). При неудаче пишет причину: DNS, тайм-аут, сброс соединения, обрыв TLS.

### Что показал отчёт `tune --bypass` и что изменено

В отчёте семь стратегий из девяти «открывали» 0 из 3, даже Cloudflare, который без обхода работал, а YouTube
не открывался нигде, хотя в браузере открывался. Наиболее вероятные причины и исправления:

1. **Проверка отзыва сертификатов.** `curl` в Windows (Schannel) отдельным HTTP-запросом спрашивает у
   удостоверяющего центра (OCSP/CRL), не отозван ли сертификат. Браузер так не делает. Эти запросы ломают и
   блокировки, и сами стратегии, и обход выглядел как «нет данных». Теперь `--ssl-no-revoke`: проверяется
   доступность, а не PKI.
2. **TLS-приёмы на порту 80.** Раньше разрезание под TLS применялось и к простому HTTP к адресам CDN, а именно
   там идут запросы OCSP/CRL. Теперь TLS-приёмы работают только на TLS-портах, а порт 80 получает отдельное
   небольшое HTTP-правило только для хостов из списков (тест `tls_tricks_never_touch_port_80`).
3. **Слепой отчёт.** (Историческая запись: в версиях с `winws` его вывод писался в `utils/winws.log`.) `tune` проверяет,
   что движок жив до и после теста, и показывает его последние строки, если он остановился.

Это объяснения по логике кода и отчёту, а не подтверждённые измерения на вашем провайдере. Запустите
`netfreedom tune --bypass` ещё раз: теперь в отчёте будет причина каждого сбоя, и по ней станет видно, верна
ли первая гипотеза.

## Шифрованный DNS: Cloudflare, Google, Quad9

Подменённый или медленный DNS провайдера связи — единственная блокировка, которую не лечит ни одна стратегия
(`tune --bypass` называет такие сайты «не лечится стратегией»), и первое, чего ждёт игровой лаунчер.
Теперь на время сессии можно включить DNS одного из трёх провайдеров:

```
netfreedom dns list                         провайдеры и их адреса
netfreedom dns bench                        замер на вашем соединении (UDP 53, TCP 443 для DoH, TCP 853 для DoT)
netfreedom dns set cloudflare|google|quad9  выбор (запоминается)
netfreedom dns set auto                     при каждом запуске берётся самый быстрый из доступных
netfreedom dns set off                      не трогать DNS системы (по умолчанию)
netfreedom start --dns google               то же для одного запуска, с запоминанием
netfreedom dns restore                      вернуть DNS вручную, если запуск завершился аварийно
```

В меню — пункт `D`. Выбор применяется после запуска движка (чтобы адреса DoH были доступны и там, где их
фильтруют) и снимается при остановке, Ctrl+C, закрытии окна, сбое и `uninstall`.

| Система | Что настраивается |
|---|---|
| Windows 11 / Server 2022 | настоящий **DoH**: адреса провайдера регистрируются с шаблоном DoH (`Set-DnsClientDohServerAddress`, автоповышение включено) и становятся DNS активных адаптеров |
| Windows 10 | в ОС нет клиента DoH, поэтому **ничего не меняется**; обычный (нешифрованный) DNS того же провайдера включается только явно: `dns set <имя> --plain` |
| Linux | `systemd-resolved` не умеет DoH, только **DoT** (порт 853): настраивается он для активного соединения. Без `systemd-resolved` ничего не меняется |

Принципы, как и во всём проекте:

* **Обратимо.** Прежние настройки (статические серверы, автоматические адаптеры, строки таблицы DoH,
  параметры соединения resolved) записываются в `utils/dns-backup.txt` до первого изменения. Если процесс убит,
  следующий запуск возвращает DNS (по pid владельца: второе окно не трогает DNS живой сессии).
  Файл проверяется строго: подделанные значения не передаются ни PowerShell, ни `resolvectl`.
* **Проверяется.** После применения идёт настоящий запрос имени; если резолвер молчит, настройки откатываются сами.
* **Живёт без прокси.** Локального прокси нет: упавший прокси оставляет машину без DNS, клиент ОС — нет.
* **Стабильно.** Каждые 15 с монитор проверяет доступность порта резолвера (в панели: `DNS … 14 ms`).
  При трёх сбоях подряд и неработающем разрешении имён (в режиме обхода) DNS переключается на следующего
  провайдера, а если не отвечает никто — возвращается прежний DNS.
* **Мягкий режим по умолчанию:** при недоступности DoH/DoT используется обычный DNS того же провайдера.
  `dns set <имя> --strict` запрещает такой откат (на Windows `AllowFallbackToUdp = false`, в resolved `DNSOverTLS=yes`).

В режиме «Игры через WARP» имена внутри туннеля разрешает сам WARP, поэтому выбранный DNS действует вне
туннеля и до подключения; переключение провайдеров в этом режиме не выполняется.

## Оптимизация для игр

* WARP-стратегии трогают только рукопожатие (UDP к Cloudflare), нулевые накладные расходы на игровой трафик.
* Игровые порты (режимы 2 и 3 обхода) получают только фейки, только в первых двух пакетах потока;
  реальные данные игры не расщепляются и не перекрываются.
* `tune` по умолчанию ранжирует по «игровой» формуле: джиттер ×3, хвост (p95 − медиана) ×0,5,
  потери ×50. Стабильные 40 мс лучше «25 мс со скачками до 90». `--plain-score` — старая формула.
* Цель измерения задаётся `--target <IP игрового сервера>`.
* Процесс движка работает с повышенным приоритетом (Windows: `HIGH_PRIORITY_CLASS`; Linux: `nice -10`,
  выставляется между `fork` и `exec`, чтобы унаследовали все потоки; нужен root, без него движок
  просто работает с обычным приоритетом). На Linux правила очереди работают в режиме fail-open
  (при падении nfqws трафик не блокируется).

### Сценарии для соревновательных игр: `warp-esports`, `warp-esports-ttl`, `warp-lowburst`

Стратегия работает только пока устанавливается соединение (и при повторном рукопожатии WARP), а не на
игровых пакетах. Поэтому она не может ускорить игру по ходу матча. Она может лишь уменьшить пачку
поддельных пакетов, которая в этот момент уходит через ваш исходящий канал: пачка из N фейков по 1,2 КБ
занимает канал на N × 1,9 мс при 5 Мбит/с и даёт скачок джиттера. Три сценария меняют размер этой пачки:

| Сценарий | Фейки на UDP 443 | Фейки на портах 500, 1701, 4443, 4500, 8095, 8443 | TTL |
|---|---|---|---|
| `warp` (по умолчанию) | 6 × 1200 Б = 7,2 КБ (≈11,5 мс) | 12 × 1250 Б = 15 КБ (≈24 мс) | |
| `warp-esports` | 3 × 1200 Б = 3,6 КБ (≈5,8 мс) | 4 × 1250 Б = 5 КБ (≈8 мс) | |
| `warp-esports-ttl` | как `warp-esports` | как `warp-esports` | 5 |
| `warp-lowburst` | 4 × 1200 Б = 4,8 КБ (≈7,7 мс) | 6 × 100 Б = 0,6 КБ (≈1 мс) | |

Время в скобках считается по размеру пачки при 5 Мбит/с, это не измерение. Хватит ли меньшей пачки,
чтобы рукопожатие прошло именно у вашего провайдера, заранее сказать нельзя: сравните командой
`netfreedom tune --quick` (она перебирает все WARP-стратегии, включая эти). `warp-esports-ttl` по TTL
рассчитан на то, что DPI стоит в первых пяти узлах; если фейки не доходят до него, рукопожатие не
пройдёт, и `tune` это покажет.

## Встроенный движок (Windows)

На Windows пакеты обрабатывает код на Rust внутри `netfreedom.exe`; внешние `winws.exe` и `cygwin1.dll`
из поставки удалены. Нужен только драйвер **WinDivert** (`WinDivert.dll` и `WinDivert64.sys` лежат в `bin/`):
перехват пакетов делает он, это код ядра, и Windows загружает его только с подписью Microsoft. Подписи у
проекта нет, поэтому драйвер остаётся тот же, подписанный. Движок запускается из процесса `netfreedom.exe`,
второй процесс с движком запустить нельзя (общесистемная защита), `netfreedom stop` завершает чужой экземпляр.
Если стратегию движок выполнить не может, он сообщает причину и не запускается: молчаливого запасного
пути через `winws` больше нет. Флаги `--native` и `--show-winws` принимаются и ничего не делают, чтобы старые
ярлыки не ломались.

**Что умеет** (всё покрыто тестами, которые идут на любой ОС, без драйвера):

- Разбор TLS ClientHello, HTTP-запросов и QUIC Initial (SNI достаётся из зашифрованного Initial: ключи
  выводятся по правилам RFC 9001, AES-GCM и SHA-256 написаны без зависимостей и сверены со стандартными
  векторами и с независимо созданными пакетами; v1, v2 и черновики).
- Списки хостов и IP/CIDR; маркеры `host`, `midsld`, `sniext+N`, `method+N`, числа.
- TCP: `fake`, `multisplit`, `multidisorder` (с `seqovl`), `fakedsplit`, `fakeddisorder`, `hostfakesplit`;
  обман `ts`, `badseq`, `md5sig`, TTL и `autottl` (TTL выводится по ответному SYN-ACK); `syndata`;
  `fake-tls-mod` из `rnd`, `rndsni`, `dupsid`, `sni=`; встроенные поддельные ClientHello и HTTP-запрос zapret.
- UDP: фейки по протоколам (QUIC, WireGuard, DHT, Discord, STUN, неизвестный), `--filter-l7`, `ipset`,
  `hostlist` по SNI QUIC, TTL, `cutoff`.

**Сверка с оригиналом.** Поведение сверялось с исходниками zapret v72.9, а не по памяти. Из этого вышло
несколько неочевидных вещей, которые движок повторяет: при `cutoff=n2` первым пакетом TCP-потока считается
SYN, поэтому игровые TCP-правила с `any-protocol` и `cutoff=n2` в winws не меняют ни одного пакета (в
движке они тоже «пустые»); `syndata` в правиле со списком хостов на SYN не срабатывает, потому что имя
хоста ещё неизвестно; `dupsid` копирует session id только при совпадении длины; `seqovl` у `multidisorder`
ставится на второй по порядку сегмент.

**Покрытие.** `cargo run --example native_coverage` разбирает все встроенные стратегии: движок принимает 36 из 36
вариантов и 370 из 370 правил.

**Известные отличия от winws:**

- ClientHello (TCP) и QUIC Initial, разбитые на несколько частей, теперь склеиваются, как `reasm` в zapret:
  первый сегмент задерживается, пока имя узла неизвестно, правило выбирается по полному имени, а
  `split`-позиции считаются по всему сообщению (куски длиннее MSS режутся по MSS). Если остаток не пришёл,
  сегмент уходит как есть через 250 мс (QUIC: 150 мс; сброс делает отдельный поток-таймер). Для правил со
  списком хостов фильтр WinDivert захватывает все исходящие данные на этих портах (как winws), для остальных
  по-прежнему только первый сегмент.
- `--dpi-desync-repeats` относится только к поддельным пакетам.
- Для `syndata` параметры TCP копируются из исходного SYN как есть, у zapret они собираются заново.
- В `fake-tls-mod` не пересчитывается расширение `padding`; `padencap` не поддерживается.
- Не поддерживаются разбор `ipcache-hostname`, `autottl6`, `orig-` и `dup-`-варианты `autottl`, автохостлисты:
  такие стратегии отклоняются с понятной причиной.
- Профиль выбирается по каждому пакету, а не один раз на поток; для UDP с `--filter-l7` это может отличаться.

**Linux.** Там по-прежнему `nfqws` и nftables: встроенного перехвата пакетов для Linux (NFQUEUE и сырые
сокеты) пока нет, поэтому `nfqws` в поставке для Linux остаётся.
